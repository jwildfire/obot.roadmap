Where qcthat stands today

  • There is one way in. CompileTestResults() accepts only a testthat result, and it is a plain function, so another package cannot add a method to it.
  • There is one kind of requirement. 36 of qcthat's 58 R files call GitHub, and the matrix joins on an issue number.
  • Human acceptance already works as evidence, but only by posing as a test. ExpectUserAccepts() opens a sub-issue and passes or fails inside a testthat test.
  • Reviews as evidence are already wanted. An open requirement asks for it and says the team is not yet sure how it should work.
  • A maintainer has already suggested making the core functions "less package-specific".

I tried it. I added a Kind column and three non-test rows to the real safety.viz results. Unmodified qcthat carried them through the matrix and a JSON round trip, so the plumbing is open. The meaning is not: the report called all of them tests, and an issue whose only evidence was a screenshot printed "All issues have at least one test". Any option past A has to fix that.

B. An evidence framework

Recommended

qcthat gains an evidence record: which requirement, what kind, what result, who, when and a link. Test results become one kind. Readers exist for each kind, the report groups by kind, and coverage counts only the kinds a project says should count.

How an extension plugs in

This is a separate choice from the scope. There are two ways, and they can coexist.

  • A file. An extension is anything that writes evidence records in an agreed format, and qcthat reads a folder of them. JavaScript, Python, a GitHub Action or a small script all qualify, and none needs R.
  • An R package. An extension registers a method on a qcthat generic. This suits R users, but a JavaScript author would have to write R to contribute.

Here is a proposed record. It borrows its shape from in-toto attestations, where each statement names a subject and a typed payload, and new types are allowed.

{
  "requirement": "jwildfire/safety.viz#334",
  "details": ["HEP-CTRL-007"],
  "kind": "acceptance",
  "label": "Release candidate 1.11.2 approved",
  "result": "pass",
  "by": "jwildfire",
  "at": "2026-10-15",
  "url": "https://github.com/jwildfire/safety.viz/pull/338",
  "source": "github-review"
}
  • The requirement is text, with the repository in it. That fixes cross-repository references, and it means a matrix row or tracker item can fill the same field if Option C ever happens.
  • details carries the matrix row IDs under Option B, so they are not lost.
  • qcthat-js becomes the first formal extension: an npm package that writes these records from Vitest and Playwright results and from the screenshot folders.
