Decisions for you

Adapter, or a JavaScript port of qcthat?

Recommendation: adapter. qcthat is about 8,000 lines of R covering GitHub fetching, reports and user acceptance. A port would rebuild that and then drift from the R version. The adapter only has to write one results file, and most of that code already exists in safety.viz.

What it costs: R has to run in one new CI job. Neither the main check nor the site build installs R today.

What counts as the requirement?

Recommendation: GitHub issues are the backbone, as you described, and the matrix rows stay as finer detail inside them. The chain becomes hub requirement, safety.viz issue, test, with row IDs such as HEP-CTRL-007 kept in the test names. There are 189 issues and 1,442 rows for what is already built, so turning rows into issues would bury the tracker.

What it forecloses: nothing. The evidence pages keep their row-by-row view.

Where does the code live?

Recommendation: in safety.viz first, then a separate qcthat-js repository when bio.viz adopts it. bio.viz has the same evidence pipeline, so it is the natural second user, and two users are what tell us the right shape. Both qcthat and qcthat-js are unclaimed on npm today.

How it would work

  1. Run tests

    Vitest and Playwright run exactly as they do now.

  2. Write results

    safety.viz writes one file in CTRF, an open test report format.

  3. Build matrix

    qcthat joins that file to the GitHub issues.

  4. Publish

    The matrix goes on the evidence pages and on each release.
  • Test names do not change. The (#N) convention is already qcthat's own.
  • The matrix step needs its own workflow. The main check runs with a read-only token, and tests/unit/ci-workflow.test.js holds it that way.
  • The matrix stays out of the evidence freshness guard, because it depends on the state of GitHub and the guard compares only test results.
  • qcthat's ready-made GitHub Action cannot be used directly, because it runs testthat. The first version is a short R script around the same functions.
  • CTRF is a deliberate choice over a private format. If qcthat later learns to read it, every language with a CTRF reporter gets qcthat, with no JavaScript in the R package.

Existing JavaScript tools

Nothing I found links GitHub issues, tests and milestones into a matrix for a JavaScript project. Downloads are npm's figures for the last seven days.

CTRF

MIT · reporter 413k/wk

An open JSON format for test results, with reporters for many languages. It has no notion of requirements. Use it as the file between safety.viz and qcthat, written from results safety.viz already parses, because its Vitest reporter was last published in September 2025.

Use

Allure Report

Apache-2.0 · 1.6M/wk

The strongest general test report, and it can attach an issue link to a test. But the link is a call inside each test, and reporters have no direct access to requirements. It would add a second report without giving you the matrix.

Skip

spec-trace

MIT · 5/wk · May 2025

The closest in spirit: it links Markdown requirements to Vitest and Playwright tests and measures coverage. It looks dormant, its README shows no GitHub issues support, and links run from the requirement to the test, the opposite of your convention.

Skip

Qase, Testomat.io, Xray

Reporters 86k–170k/wk

Reporters for hosted test management products. Xray keeps requirements in Jira. The record of what was required would move out of GitHub, which removes the point. I did not evaluate their GitHub integrations.

Skip

OpenFastTrace, LOBSTER, reqstool, StrictDoc, Doorstop

Java and Python

Serious traceability tools, some built for safety standards. They keep requirements in their own files, and none is a JavaScript tool. Adopting one would replace qcthat on this half of the stack, so the R and JavaScript sides would stop matching. OpenFastTrace is GPL and LOBSTER is AGPL.

Skip

Cucumber, playwright-bdd

MIT · 889k–2.1M/wk

Requirements written as Gherkin scenarios. That would mean rewriting 2,982 tests.

Skip

Playwright annotations, Vitest tags

Built in

Structured places to put an issue number. They are cleaner than parsing names, but evidence files are keyed on test names, qcthat parses names, and the convention is already in place. Keep this in mind only if names become a problem.

Not now

What this does not do

The matrix does not qualify a chart. Every chart keeps its current tier. The matrix shows that a test exists and passed for an issue, and it cannot say whether the chart is clinically right.

  • A single passing test turns an issue green, so issue coverage is a weaker claim than row coverage. Today 1,215 of 1,442 rows have a test that names them. Keep that figure on the evidence pages beside the matrix.
  • Screenshots stay on the evidence pages. qcthat has no place for them, so each test in the matrix should link to its evidence page.
  • qcthat's ExpectUserAccepts() user acceptance flow is tied to testthat. It is out of scope here.
