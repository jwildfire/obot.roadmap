THE SITUATION

Three sentences

The safety census is one exported function, two hundred and seventy-seven lines long, that reads five raw tables and returns every denominator a safety reader needs — how many participants, how many dosed, how much person-time, who left and why, and how completely the data was collected. An adversarial review confirmed that several of those figures are silently wrong, most seriously a death count that reports one where the same study's records hold thirteen. You decided it stays and gets rebuilt so that each number becomes a metric the pipeline computes and can be checked on its own, and the census becomes a report over those metrics.

What you said, dictated on 18 August:

“I think that we should model it after the gsm.kri report, where these core numbers that right now are clearly wrong are metrics. Not every metric has to have an action associated with it. So number of deaths should be a metric, not some code wrapped deep in the safety census function. Right now those three safety metrics we have are all, in theory, actionable and flaggable, but that's not the only point of metrics. The point of metrics is to have trustable numbers that we can qualify and validate.”
The sentence the design is built on

A metric with no action is not a lesser metric. Everything below follows from taking that literally: the death count, the enrolment count and the person-time totals go into the same machinery as the flagging metrics, get the same specification, the same intermediate tables and the same independent inspection, and simply never raise anything.

THE PART THAT MAKES IT CHEAP

A metric with no action already exists

The obvious objection to a descriptive metric is that the framework will not take one: the flagging step refuses to run without a threshold, and the step after it insists on a flag column. Both are true, and neither matters, because the risk-score metric in the key-risk-indicator package already goes around them. It declares no threshold, calls no flagging step, and publishes its rows with the flag left empty. It has been doing that in production the whole time.

Three consequences, and they are the reason this is a modest build rather than a framework change:

  • An empty flag, rather than a zero, is already the ecosystem's way of saying this number does not flag. A zero would mean measured and found fine — a green light nobody meant to give.
  • The risk-score builder ignores any metric that carries no threshold, automatically. A descriptive metric cannot accidentally move a site's risk score, which is exactly the property you described when you said the participant metrics should not.
  • Nothing upstream needs to change. Everything the design needs sits in packages we do not own and must not edit; none of it has to be touched.

So a census metric is an ordinary metric definition with the threshold lines simply absent, plus one small helper in our own package that stands where the flagging step would be and marks the row as not flagging. That helper is about ten lines, and it is the only genuinely new mechanism in this design.

THE SHAPE

What replaces the function

Three layers, each one a thing the pipeline already knows how to run.

One. Thirteen metric definitions, one per number

Each census figure becomes its own metric definition file, named and numbered the way every other metric in the ecosystem is, and each declares the exact columns it reads from the standardised study domains. Declaring them is what fixes the largest class of defect: a column that is missing stops the metric with an error instead of quietly reporting zero.

Every one of them uses the standard rate step, which anchors the count to the enrolled participants and looks the rest up against them. That single choice fixes two separate defects at once: a participant identifier that appears in a disposition record but was never enrolled cannot be counted, and the count and the denominator can no longer disagree, because they come out of the same operation. The published row carries the count and the denominator side by side, which is exactly the pair the census displays.

Two. One report definition

The census report becomes a report workflow of the same kind the key-risk-indicator report already is: it declares the tables it needs, and its steps call helper functions that assemble and render. It reads the metric results the pipeline produced rather than recomputing anything, so there is no second counting lane and no way for the census to disagree with the rest of the package about the same study.

Two things the metric layer genuinely cannot express stay in the report, and the design says so rather than pretending otherwise:

  • The median days on treatment. A median is not a count over a denominator. The report computes it from the exposure metric's own published per-participant table, so it is reproducible from an intermediate anyone can download, but it is a presentation rather than a metric. Making it one would need a new averaging step, which is a bigger change than it is worth today.
  • The reasons participants discontinued. Those are free text and cannot be enumerated in advance, so the counted states are metrics and the reason breakdown is a table the report builds. The blank-reason bug goes with it: a missing reason reads as “reason not recorded”, never as the literal word for a missing value, which is what it prints today.

Three. The name, kept

The function survives as the one-call front door: it runs the census metric workflows over the domains it is handed, assembles the same three tables it returns today, and hands them back. What disappears from it is the arithmetic — every number inside it moves out into a metric definition that can be run, inspected and checked on its own. What survives is the convenience, which is the part anybody actually calls.

WHAT MOVES UNDERNEATH YOU

What breaks, stated specifically

The interface barely moves. The numbers move a lot, and that is the real cost of this rebuild, so it is worth being exact about it.

The calls

  • There is exactly one caller anywhere: a script in the demo study, which passes five standardised domains and no column names. Under the recommended answer to the fifth question it keeps working untouched.
  • The sixteen-parameter signature is what costs. Eleven of those parameters name columns, and they are the mechanism the review found untested and dialect-wrong. Keeping them working while the columns are declared elsewhere means keeping them as a deprecation notice: they are accepted, they warn, and they are ignored. That is a real piece of debt with a real removal date attached.
  • An alias alone would be cheaper, but it would not satisfy what you asked for. An alias preserves the name; it does not preserve the call. The recommendation preserves both, which is why it is the more expensive of the two and still the right one.

The figures on the public demo page

The demo's safety overview reads the census payload live. These figures change the day this ships, and every one of them changes because it was wrong:

  • Deaths goes from one to thirteen, or to absent, depending on how the first question is answered. This is a published clinical figure on a public page changing by more than a factor of ten. It is the entire reason the rebuild exists, and it is also the thing that will look alarming to anyone who sees the before and after without the explanation.
  • Randomised participants stops being read from the demo's private arm column and starts being read from the randomisation domain, which the demo does not currently map. On today's inputs it would go from a number to absent.
  • The expected count in the coverage table stops being total enrolment repeated at every visit, which is a fiction on any study with staggered enrolment.
The failure mode to design against

The demo application looks up four census rows by their exact wording — enrolled participants, received study drug, person-years on treatment, and deaths. If any of those labels is reworded, the tile does not error; it disappears. That is the silent-success shape this program keeps meeting, so the wording of those four is treated as a contract with a test behind it, and any rewording ships in the same release as the application change.

C1 · deaths

Which record decides how many participants died?

There are three answers in the ecosystem's own bundled study and they are one, twelve and thirteen. One is what the census reports now, by matching the word for death in a free-text discontinuation reason. Twelve is the dedicated table of death records. Thirteen is the standard mapping's combined figure, which unions the two — twelve participants with a death record, plus one whose discontinuation reason says they died but who has no death record at all. That last participant is the interesting one: the sources genuinely disagree about a real person.

  • Death domain. The metric reads the death records and nothing else. A study that does not supply them reports no death figure rather than a wrong one — including the demo, which does not supply them today and would need the file added.
  • Both, combined. The metric uses the standard mapping's union of the two sources, which is the ecosystem's existing definition and gives thirteen. Nothing new needs to be decided about what counts as a death, because the mapping layer has already decided.
  • Both, and their disagreement is its own number. The union is the death count, and a second descriptive metric publishes how many participants the two sources disagree about. On this study it would read one, which is a data-quality signal rather than a nuisance.
Recommendation: both, and their disagreement is its own number. The union is not our invention, so we are not inventing a clinical definition; and the disagreement count is nearly free once both sources are already in hand, is exactly the kind of number that has no action attached, and is the first thing a monitor would want to know. The cost, either way, is that the demo study has to start supplying death records — a file it does not have today.
C2 · coverage

What does “expected” mean in the coverage table?

The coverage table is the part of the census with no counterpart anywhere else in the ecosystem, and the review judged it the idea most worth keeping: it reports, per visit, how many participants have a result against how many should. The trouble is the second half. Today “should” means total enrolment, repeated at every visit — so a study that enrolled half its participants last month looks like it is missing half its data.

  • Time on study. Expected means the participants whose time on study reaches that visit. Computable from what every study already supplies, no new data anywhere, and honest about staggered enrolment.
  • The visit schedule. Expected means the participants with that visit actually scheduled, read from the visit domain. This is the real answer clinically, and it costs the demo a domain it does not map today.
  • Leave it as enrolment, and say so. Cheapest, and the figure keeps a meaning nobody would guess, which is how it got here.
Recommendation: time on study. It is right for every study without asking any study for anything new, and it removes the alphabetical-visit-ordering defect on the way, because coverage stops keying on whatever visit label the lab rows happen to carry. The visit schedule is strictly better and is the natural follow-on once a study maps it — the design leaves the door open by making the expected-count source a declared input rather than an assumption.
C3 · thresholds

Does any census number raise a flag?

Your sentence says a metric does not need an action. It does not say none of them may have one, and there is one plausible candidate: data completeness. A visit where a large share of participants have no result is a monitoring finding in its own right, and it is the figure the coverage table exists to surface.

  • None. Every census number is descriptive. The census never raises anything, and any thresholds are a separate decision later.
  • Completeness only. Data completeness carries a threshold and can go amber; everything else stays descriptive.
  • Decide per number later, once the numbers have been checked against a real study.
Recommendation: none. Not out of caution — because a threshold is a clinical cut-point and nobody has set one for data completeness, so choosing a number now would mean inventing it. Building the census entirely descriptive also demonstrates the thing you said the framework is for, on thirteen numbers at once. A completeness threshold is a small addition afterwards and would arrive with a reason attached.
C4 · level

Study only, or sites too?

The census answers about the study. The report you named as the model answers about sites. The metric framework computes at whichever level it is told, and the ecosystem's usual practice is to write the same metric out once per level rather than adding levels up — because some figures, medians among them, cannot be added up correctly.

  • Study only. Thirteen definitions. This is what the census is and what the demo shows.
  • Study and site. Twenty-six definitions, each site's figures computed from participants directly rather than rolled up. Every census number becomes comparable across sites, which is what would make the report chart-worthy.
  • Study, site and country. Thirty-nine, matching the levels the key-risk-indicator metrics already run at.
Recommendation: study only, built so the level is a setting. The census's job is a standing study summary, and the first release should make its numbers trustable rather than multiply them. Adding sites afterwards is a copy of each definition with one line changed, not a rewrite — provided the level is a declared setting from the start, which is the part this recommendation is actually asking for.
C5 · compatibility

Does everything keep working through the change?

Two contracts exist. One is the function's own arguments. The other is the compact file the pipeline writes and the demo application fetches, whose shape and whose row labels the application depends on.

  • Nothing breaks. The old arguments are still accepted, with the column names deprecated and ignored, and the report keeps writing the same file in the same shape. The demo application is untouched by this release and its figures simply become correct.
  • The name survives, the shape does not. The function takes the pipeline's results instead of raw tables, the file is replaced by the standard results tables, and the demo application moves in the same release.
  • Deprecate and remove. The function warns for one release and is removed in the next, with the demo migrated in between.
Recommendation: nothing breaks. It is what you asked for — the function kept, not merely the name — and it means the release that changes what the numbers say does not simultaneously change how anything reads them, so if a figure looks wrong afterwards there is exactly one place it can have come from. The second option is a good follow-on once the numbers are trusted; doing both at once makes any problem twice as hard to locate.
C6 · charts

Does this release draw anything?

You said the census probably becomes a report, perhaps with charting functions, and that the way charts are done in the two chart libraries today is fine for this. The coverage table is the one part that genuinely wants a picture. Where it gets built is the question, because our own chart library carries a completion bar: a new chart is not finished until it has a gallery demo, an evidence page, an interface reference and a binding in the R package.

  • No chart. The report is tables and figures, rendered in the report itself. Charts become their own requirement, with the coverage chart as its first item.
  • Reuse. The coverage chart is drawn with the existing bar chart from the key-risk-indicator side, which needs no new chart work at all — but it does add a package dependency, on a repository we do not own and cannot install from reliably in our own automation.
  • Build it properly. A coverage chart in our own chart library, through the full four-part gate.
Recommendation: no chart, and file the chart requirement in the same breath. This release's job is making thirteen numbers trustable, and a proper chart is a piece of work of comparable size to the rest of it. Deferring it costs nothing if it is filed rather than remembered — and your own rule is that one requirement covers one release.

What unblocks on each answer

  • Deaths — the death metric is the first thing built, and it is the one that proves the whole design. It also tells the demo study whether it needs a new input file, which is work outside gsm.safety.
  • Coverage — the coverage metric's inputs are settled, and with them the visit-ordering fix.
  • Thresholds — the metric definitions can be written; a descriptive one and a flagging one differ by three lines, so this is the cheapest question to answer and the one blocking the most files.
  • Level — how many metric definitions get written. Nothing else changes shape.
  • Compatibility — whether the demo study and its application are in this release's scope or a later one.
  • Charts — whether the chart library is in scope at all. Answering “no chart” closes the whole question and files a follow-on.

Nothing was blocked on all six, and in the event all six were answered at once — so nothing on the list above is waiting on him any longer. What the build now waits on is his review of the implementation itself, which is a separate gate: gsm.safety is clinical work and he sees it before production.

AFTERWARDS

How it would get built, and how you would know it worked

Four steps, in this order, each landing as its own piece of work under the requirement. The order matters: the death count comes first because it is the number the review was written about, and until it is right nothing else about this rebuild has been demonstrated.

  • The death metric, alone, with the small not-flagging helper it needs. One metric definition, one helper, tests. This is the proof that a descriptive metric runs end to end and lands beside the flagging ones with nothing downstream disturbed.
  • The remaining twelve, written against the same pattern, with the duplicate-row and never-enrolled tests applied to each.
  • The report workflow and its helpers, reading the results the metrics produced and computing nothing of its own — including the compact file the demo reads, if compatibility is answered that way.
  • The function, rewritten to run the workflows and return the tables it returns today, with the column arguments deprecated.

How it is checked is not a matter of the tests passing. Each number is checked against the same study through a second route — the death count against the death records read directly, the enrolment count against the subject table, the coverage figures against the raw domain — and the check is recorded. That is what qualifying a number means, and it is the part your sentence about validation is actually asking for. A test that the code does what the code does would not have caught any of the defects in the table above.

One thing worth saying plainly

The published figures change when this ships, and the largest of them is a death count going from one to thirteen on a public page. Under your transparency rule the release notes name every figure that moved and why it was wrong before — not as a footnote, as the substance of the release. A safety tool quietly correcting a death count is worse than one that never had the bug.
