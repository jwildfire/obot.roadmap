How prime remembers: six calls, latency-first

🎩🤖 obot-prime is a standing singleton designed to stay up indefinitely, which makes context compaction a certainty, not a risk. Its charter asserts that "durable state lives in the scratchpad and in the delegates' artifacts, never only in prime's context" — an assertion with no mechanism behind it, and tonight produced a live instance of the failure class it invites. This page turns the assertion into a mechanism, under one binding constraint: the <30-second reply is the objective function, not a tiebreaker. It also evaluates @jwildfire's mid-session proposal of a standing Navigator agent head-to-head against the file-based designs, on the same terms. Every recommendation is measured or cited.

The ask, in one screen

C1Split queryable STATE from the append-only narrative log?
→ Recommend yes: a capped prime-state.md — five sections (Open / Delegates / Armed / Claims / Settled), ~4 KB hard cap, a provenance stamp on every line ([verified gh 23:41] vs [asserted 👯🤖 news-rc]), lines deleted on resolution. The log stays as-is: it answers "what happened"; the state file answers "what is true right now".
C2Is state kept true by a standing "Navigator" peer agent?
→ Recommend yes — but only as a file-writer, never as someone prime asks. Day-one scope: verify-and-stamp bookkeeping only; standards enforcement as observe-and-report, not correction; audits stay in their existing lane. Ramp from a scheduled verification sweep (tonight's 22:51 sweep is the working prototype — it caught the stale oa#83 claim) to a standing session only if cadence demands it.
C3What is the rehydration procedure after compaction or relaunch?
→ Recommend one scripted bundle read (prime-rehydrate, mirroring the proven handoff.sh): state file(s) + today's log + sweep cache in a single ~7k-token, one-round-trip read — 0.35 s wall, measured. Fired lazily, on the first post-compaction turn that touches state. Trust the compaction summary for flavor, the bundle for facts.
C4Are per-event writes at the right cost?
→ Recommend script-ify the heartbeat: the 759-char Bash+python heredoc costs ≈190 generated tokens (≈2–3 s) per event; a scratchpad-log call costs ≈20. ~10× cheaper, and every sibling benefits.
C5What does prime deliberately let go?
→ Recommend four retention rules: answered Q&A is gone once relayed; delegate reports reduce to a pointer; GitHub state is pointed at, never copied; settled decisions live as one ## Settled line until applied, then deleted.
C6Where does this land?
→ Recommend one obot.agent PR (skill section + link-only framework section + two scripts + template edit), left open for review — and the Navigator as a hub requirement issue, drafted through the requirement lifecycle rather than smuggled into the same PR.

C1 gates C3 and C5 (both operate on the state file). C2 composes with C1 — the Navigator needs the state file to write into. C4 is independent and pays across every sibling. C6 is the vehicle.

The situation

Prime launched tonight (2026-08-14, 22:44) as the standing Q&A concierge: one long-running session reachable from terminal or phone, whose only product is fast answers — <30 seconds, ≤2 sequential round trips, everything else delegated. Working sessions die at their wrapup and are reborn through session-init's hand-off; prime has no bookends and no rebirth. When its context fills, the harness summarizes the conversation and continues — and per Anthropic's documented compaction contract, what survives on purpose is what lives on disk; what was only ever said in conversation survives only if the summary happens to keep it.

That compaction summary is written by the harness, not by prime: prime does not choose what survives it, cannot audit what it dropped, and cannot re-derive what was never written down. The charter's answer — durable state lives outside the context — is correct doctrine with no mechanism: nothing says what gets written, when, in what shape, or how a freshly-compacted prime gets back to useful without blowing its own latency contract.

Mid-drafting, @jwildfire added a design intuition, relayed through prime: "we probably need a separate 'Roadmap bot' running in the background… call it the 'Navigator'… watching the roadmap for current state and keeping everything up to date for you. I might also delegate the audit updates to the navigator. Its job is to make sure that all of the worker agents are following our github standards and to keep track of current state of the work being done (so that you don't have to)." That is a concrete architectural answer to this exact question — externalize state into a peer agent rather than only into files — and it is evaluated head-to-head in C2, not footnoted.

The incident to design against. At 22:50 prime armed an RC-watch monitor and told @jwildfire it "self-corrects". That was false — the monitor was broken on arm (a zsh word-splitting bug; it was watching nothing) and the finding prime credited to it had actually come from a separate one-off verification sweep. The claim was made inline and never written down, so no record on disk existed to contradict it; it took a peer session independently catching the broken monitor (22:53) to surface the error. A claim that exists only in prime's context is unfalsifiable by anything on disk — and after compaction, it can survive as confident summary-fact with its provenance gone.

And it was not alone. Tonight produced three further provenance errors, every one a summary-of-a-summary: a close-out line reported oa#83 "still open" when it had merged hours earlier (stale self-report, caught by the 22:51 verification sweep); prime's own sweep then misread a creation timestamp as the merge time (corrected by a peer at 23:10); and a peer attributed the hub's two unpushed commits to prime when they were the closing lead's (corrected at 23:10). None of these were lies — each was an agent confidently repeating derived state without a provenance stamp that would have made it checkable. That pattern, not any single mistake, is what the mechanism below must fix.

What the numbers mean

  • Disk I/O is ~0% of the budget. The entire candidate rehydration set reads in under 2 ms. File size is not a latency problem at these scales — round trips and generated tokens are the whole budget.
  • The round-trip arithmetic. The contract allows ≤2 sequential round trips per reply. A cold (post-compaction) turn that needs state therefore has exactly one spare round trip for reading before the answering trip. Rehydration must be a single batched read; two reads breaks the contract by itself. (Per-round-trip wall time for an Opus-class lead at working context is on the order of 5–15 s — an estimate from tonight's observed turn cadence, marked as such — which is why 2 round trips ≈ the 30-second ceiling.)
  • Generated tokens are the hidden per-event cost. Output generation is the slow direction (~tens of tokens/second). The 759-character heartbeat heredoc is ≈190 tokens of generation per log event — ≈2–3 s each time, plus permanent context burn, since every tool call stays in context.
  • Context burn is second-order latency. Every KB prime re-reads recurringly advances the next compaction, and each compaction costs a summarization pass plus a rehydration. There is also a documented cache cliff: a session idle past the prompt-cache lifetime (1 hour on subscription) reprocesses its full context on the next message (Anthropic, Claude Code costs) — for an agent answering sporadic phone questions, that post-idle first reply is the worst case, and it scales with context size. A bounded working set makes the cliff shallower every time.
  • The budget, stated: a cold turn may spend one Bash/Read round trip ingesting ≤ ~8k tokens from ≤ ~30 KB of files, then answer. The recommended bundle (state ~1k + today's log ~4k + sweep cache ~2k ≈ 7k tokens, <30 KB, 0.35 s) fits with margin. Tonight's 17 KB scratchpad alone would fit; 07-28's 67 KB (~16.7k tokens) would not — which is why "just re-read the log" is not the answer.

What the field says

A background research pass swept Anthropic's documentation and engineering posts plus the third-party agent-memory literature. The load-bearing findings, each with its source:

  • Only disk-backed state reliably survives compaction — and the harness reloads it free. Anthropic documents exactly what survives a compact: the system prompt is unchanged, project-root CLAUDE.md and the auto-memory MEMORY.md index are re-injected from disk, and anything said only in conversation survives only if the summary keeps it (context-window docs, memory docs). The working set must live on disk; conversation is not storage.
  • "Assume interruption" is the vendor's own operating doctrine. The system-prompt protocol Anthropic auto-injects with its API memory tool reads: "ASSUME INTERRUPTION: Your context window might be reset at any moment, so you risk losing any progress that is not recorded in your memory directory" (memory-tool docs). Prime's charter assertion is this doctrine; the mechanism below is its implementation.
  • Snapshot + log is Anthropic's published pattern for long-running agents. Their harness guidance has an initializer write a structured current-state file plus an append-only progress log, and every session resume by reading them; "compaction alone isn't sufficient" without this scaffolding (effective harnesses post). The same post prefers JSON for worker-fleet state because models tamper with it less — an honest point against the Markdown choice in C1, answered there.
  • Index-eager, detail-lazy is the sanctioned retrieval shape. Auto-memory loads only the first 200 lines / 25 KB of the index and fetches topic files on demand; the context-engineering post generalizes it as "just-in-time" retrieval via lightweight identifiers (memory docs, context engineering post). A post-compaction answer should need one fast read, not a re-exploration.
  • Context rot is empirical, and it argues for small. Model recall degrades as in-context tokens grow — treat attention as a finite budget (Anthropic); Chroma's 18-model evaluation shows reliability degrading well below nominal window limits (context-rot research). A 1k-token state file is not just faster than a 17k-token log replay — it is more accurately read.
  • Summaries are contaminated ground truth. A mis-summarized detail "propagates forward as if it were ground truth" (zylos); LangChain's deep-agents work names goal drift and false completion claims as compaction failure modes and recommends stress-testing recovery by compacting early (deep agents post); Cognition's argument against dispersed context — summaries of summaries lose the implicit decisions — is precisely tonight's three provenance errors (Cognition). Steering exists (/compact <instructions>, a # Compact instructions heading in CLAUDE.md — docs) and is worth using, but Anthropic's own belt-and-suspenders advice is to pair compaction with external memory, never rely on the summary alone (memory-tool docs).
  • The measured upside is large. On Anthropic's agentic-search evaluation, memory + context management beat the baseline by 39%, and context editing alone cut token consumption 84% in a 100-turn evaluation (Anthropic announcement).
  • The industry working-set/archive split maps one-to-one onto this scaffold. Letta/MemGPT's tiers — capped self-edited in-context "core memory", searchable interaction history, external archival store (Letta) — and LangGraph's checkpointer-plus-store (LangGraph persistence) correspond to: prime-state.md (core, missing today) / scratchpad + transcripts (history, exists) / GitHub + artifacts + memory (archive, exists). The scaffold has every layer except the core one.

The six decisions

C1 · gates C3 and C5

Does prime get a queryable STATE file, separate from the narrative log?

Why now: tonight's log is good narrative that cannot answer "what is open right now" without a full replay plus mental correction-folding. Compaction makes that replay a recurring cost, and makes the un-replayed alternative — trusting the summary — exactly the confidently-stale failure mode.

C1-a · Status quo: log + compaction summary

What
Keep appending narrative; let the harness summary carry the working set across compaction.
Costs
Rehydration = whole-log replay (~4.3k tokens tonight, ~16.7k on a 07-28-scale night) with corrections folded by the model each time; or trusting a summary prime neither writes nor audits. The "self-corrects" class survives intact.
Forecloses
Nothing — which is the problem; it also forecloses nothing for the failure modes.

C1-b · A capped prime-state.md, provenance-stampedrecommended

What
.claude/session-hub/prime-state.md: five bulleted sections — Open (pending items, one line + link each), Delegates (slug · lane · told-to-do · status), Armed (monitor ids, cadence, re-arm notes), Claims (assertions made to @jwildfire), Settled (do-not-relitigate, with provenance). Every line carries a provenance stamp: [verified gh 23:41] / [asserted 👯🤖 news-rc 23:20] / [self, unverified] / [corrected 22:53] — written for the reader who must decide whether to repeat the claim to @jwildfire. Hard cap ~4 KB (~1k tokens); resolved lines are deleted — the log keeps history. One line in MEMORY.md points at the file and the rehydrate procedure, making the mechanism itself compaction-proof (the index is re-injected from disk after every compact). Prime is sole writer of its sections, so section-replacing edits are safe under the multi-writer rules.
Costs
One Edit per state change — batched into the same message as the reply that changes it, so zero added round trips. Discipline: the cap must be enforced or this becomes a second scratchpad. On Anthropic's JSON-over-Markdown point: that guidance targets worker fleets resuming each other's state cold; prime is a singleton sole-writer whose file doubles as a human-glanceable dashboard for @jwildfire, and Markdown keeps the write cheap inside a reply. If tampering is ever observed, switching the file to JSON is a mechanical change.
Forecloses
Treating the log as the query surface. It also makes prime's claims falsifiable — deliberately.

C1-c · Structured JSON state

What
The same content as machine-parseable JSON (shape-checked, tool-queryable).
Costs
Prime is the only consumer and reads Markdown natively; JSON adds escaping/rewrite friction on every update with no query engine to exploit, and loses the over-the-shoulder readability a concierge's state file gets for free. (Anthropic's tamper-resistance argument for JSON is acknowledged in C1-b and revisited if the Navigator becomes a second writer.)
Forecloses
Cheap hand-editing and casual inspection; buys little until a second machine consumer exists.
Recommendation

C1-b — the capped, provenance-stamped Markdown state file.

This is the snapshot/log split — Anthropic's published long-running-agent pattern and Letta's "core memory" — applied at exactly prime's scale: the log remains the append-only record of what happened; the state file is the ~1k-token snapshot of what is currently true, with every line carrying how it is known. The write is free at the latency margin because it rides the reply message, and the Claims section is the direct fix for the "self-corrects" incident: the rule becomes "if it's worth telling @jwildfire, it's worth one stamped state line, written in the same message" — making every claim falsifiable by disk before it can fossilize into a compaction summary.

Unblocks
C3's one-read rehydration, C5's retention rules, and C2's Navigator — which needs a stamped state surface to keep true.

C2 · @jwildfire's proposal · composes with C1

Is state kept true by a standing "Navigator" peer — and what may it own?

Why now: @jwildfire, mid-session: a background Roadmap bot "watching the roadmap for current state and keeping everything up to date for you", possibly owning audit updates and GitHub-standards enforcement across worker agents, "so that you don't have to". Evaluated here on the same latency-first terms as everything else. The blunt architectural fact first: a peer prime must ask is strictly worse than a file prime reads; a peer that writes the file prime reads is strictly better than prime maintaining everything alone. Which of those the Navigator is decides whether it helps or hurts.

C2-a · Navigator as someone prime asks

What
Prime forwards state questions to the Navigator over the session-to-session message lane and relays its answer.
Costs
Every answer waits on a cross-session round trip plus the peer's own model turn — seconds to minutes, and unbounded if the Navigator is mid-task. That breaks the ≤2-round-trip / <30 s contract on its face. Worse, it is a summary-of-a-summary lane: prime would fluently relay a peer's curated view with no way to distinguish verified fact from confident inference — the exact shape of all four of tonight's errors, now institutionalized.
Forecloses
The latency contract and the provenance fix simultaneously. Never this.

C2-b · Navigator as a verifier that writes staterecommended

What
The Navigator's product is a file, not a conversation: on a cadence it verifies the working set against live GitHub and writes navigator-state.md beside prime's file (two files, each single-writer — no multi-writer hazard) — upgrading stamps to [verified gh HH:MM], flagging drift (stale claims, items that moved, standards violations) as report lines. Prime's rehydration bundle picks it up in the same one read at ~0 marginal cost (0.2 ms/file, measured). Day-one scope: job (a) only — read-only bookkeeping and verification. Job (b), standards enforcement, is observe-and-report: the Navigator files what it sees (state lines, issues); it never corrects another agent's work, because a bot that polices peers can be wrong about them — tonight two careful agents disagreed about whether a merge-lane denial even reproduced — and the recourse for a wrong report is a reply, while the recourse for a wrong correction is an incident. Job (c), audit updates, stays in its existing lane (the local audit framework) until (a) has proven reliable; migrating it is a later, separate call. Ramp: start as a scheduled verification sweep — tonight's 22:51 one-off sweep is the working prototype, and it caught the stale oa#83 claim — and graduate to a standing session only if cadence and scope demand one.
Costs
Another agent to operate, with the fragility tonight demonstrated (the monitor that was broken on arm and dies on retirement): the Navigator needs its own proof-of-life line in state, and its absence must degrade gracefully to prime's self-stamps. Navigator errors remain possible — mitigated because every line it writes is stamped and therefore checkable, unlike a spoken answer.
Forecloses
Nothing: it composes with C1 rather than replacing it, and the ramp means no standing session is built before a cron sweep has earned it.

C2-c · No Navigator: self-maintained state + ad-hoc sweeps

What
Prime maintains its own state file and launches one-off verification sweeps when it judges them worthwhile (tonight's pattern).
Costs
Verification happens only when someone thinks of it, so freshness is lumpy and the [verified] stamps age unpredictably; prime carries bookkeeping for cross-agent state, which grows with fleet size — the exact burden @jwildfire is proposing to lift.
Forecloses
Nothing — this is the graceful-degradation floor that C2-b falls back to when the Navigator is down, and the sensible interim while C1 beds in.
Recommendation

C2-b — yes to the Navigator, strictly as a file-writing verifier, scoped to bookkeeping on day one, ramped from a scheduled sweep.

The head-to-head is not Navigator versus state file: a Navigator only works as a writer of the state surface C1 creates, and it answers the one weakness of self-maintained state — that self-reports go stale and nobody re-verifies them (all four of tonight's provenance errors). One boundary is non-negotiable: the Claims section stays prime's own. Only prime knows what it just told @jwildfire; the "self-corrects" claim was invisible to any GitHub watcher by construction, so the write-with-reply rule stands regardless of how capable the Navigator becomes. And enforcement stays observe-and-report until there is a track record — the standard for a bot that judges other agents should be the same one this page applies to prime: every judgment written down, stamped, and checkable.

Unblocks
@jwildfire's "so that you don't have to" — prime stops carrying cross-agent bookkeeping — without ever putting a peer agent on the response path. Approving C2-b also settles where audit updates do not go yet.

C3 · the heart of it

What exactly does a compacted prime run to get back to useful?

Why now: the budget allows one read round trip on a cold turn. The question is what that one read contains, and whether it fires eagerly (every post-compaction turn) or lazily (only when a question touches state).

C3-a · Re-read the whole scratchpad

What
On a cold turn, read today's full scratchpad (plus yesterday's, per the pointer-chase guard) and reconstruct state from narrative.
Costs
~4.3k tokens tonight, ~16.7k on a heavy night, growing all day; reconstruction (folding corrections, inferring status) is model work done inside the latency budget, every time. Unbounded by design.
Forecloses
Predictable cold-turn latency.

C3-b · Scripted bundle: prime-rehydraterecommended

What
A ~30-line sibling of handoff.sh: emits prime-state.md (+ navigator-state.md if C2-b lands) + today's ## Session log + gh-sweep.json, ===-delimited, ages precomputed. One Bash call, ≈7k tokens, measured pattern cost 0.35 s wall. Fired lazily: on the first post-compaction turn whose answer touches state scope; pure-lookup questions (conventions, where-does-X-live) skip it. Also wired as /s-prime preprocessing so a relaunch rehydrates with zero round trips — the same Tier-0 trick that took init toward its <10 s bar. Complement, not substitute: a # Compact instructions block (a documented harness feature) steering summaries to keep roster/queue/corrections makes the summary better, but the bundle stays the authority.
Costs
Writing and maintaining one small script. The lazy trigger requires prime to notice "this question touches state" — a judgment call, but a cheap one, and the failure mode (rehydrating unnecessarily) costs one round trip, not correctness.
Forecloses
Nothing; C3-a remains the degraded fallback if the script is missing (every source optional, always exit 0, handoff.sh-style).

C3-c · Trust the compaction summary, read nothing

What
Fastest possible cold turn: zero extra round trips; lean on the harness summary alone, reading files only when an answer visibly needs them.
Costs
The summary is unaudited and uncontrolled — this is the one option that preserves the "self-corrects" failure class, now with provenance stripped. The literature's word for this is contamination: a mis-summarized detail propagates as ground truth.
Forecloses
The ability to promise @jwildfire that post-compaction answers about program state are grounded.
Recommendation

C3-b — the lazy scripted bundle.

It is the only option that is simultaneously bounded (≤ ~7k tokens, one round trip, fitting the ≤2-round-trip contract with the answering trip to spare), grounded (state comes from disk, not from the summary), and honest about cost (0.35 s wall, measured on the identical handoff.sh pattern; sub-2 ms of that is I/O). The compaction summary is still used — for conversational continuity, which it is good at — just never as the authority on state. The one-line version: trust the summary for flavor, the bundle for facts.

Unblocks
Compaction stops being an event prime fears or even notices much: cold turns cost one bounded read, relaunches cost zero. The charter's longevity clause becomes true by mechanism instead of by assertion.

C4 · independent · pays across all siblings

Is a 759-character heredoc per log event the right write cost?

Why now: the heartbeat heredoc (briefing template) is generated fresh by every agent on every event: ≈190 output tokens ≈ 2–3 s of generation each time, plus permanent context burn, plus 759 characters embedded in every sibling briefing. Prime logs a lot (14 events tonight); under latency pressure the temptation is to skip a write — and a skipped write is exactly how the "self-corrects" class is born.

C4-a · Keep the heredoc

What
Status quo: self-contained, zero dependencies, works even if obot.agent is missing.
Costs
≈190 gen-tokens/event; tonight's 14 prime events ≈ 2,700 tokens of pure boilerplate generation (~30–45 s cumulative) and the same again in context burn. Every spawn prompt carries the block.
Forecloses
Nothing; it is just the expensive way.

C4-b · scratchpad-log scriptrecommended

What
Move the exact python (heading-anchored insert, section-drift guard, shelled timestamp) to obot.agent/tools/scratchpad-log. A log event becomes scratchpad-log '👯🤖 slug' 'event text' — ≈20 generated tokens, ~10× cheaper, identical semantics. The briefing template shrinks by the whole code block and gains one line. Needs one allowlist entry in workspace settings — @jwildfire's edit to make, same carve-out lane as tonight's merge-lane fix.
Costs
A script to maintain; a graceful-degradation line in the template (fall back to the heredoc if the script is absent). The allowlist edit is a manual step for @jwildfire.
Forecloses
Nothing — the heredoc remains the documented fallback.
Recommendation

C4-b — script-ify, for everyone.

This is the one change in the page that makes writes cheaper rather than adding any — it lowers the marginal cost of the exact behavior (write-with-reply, every claim, every event) that C1 depends on. When logging costs ≈20 tokens inside the same message as the answer, "too busy to log it" stops being a real pressure, which is the honest mitigation for the skipped-write failure mode: make the right thing nearly free instead of exhorting discipline.

Unblocks
Cheaper heartbeats for every sibling and ultracode job, a ~750-character-lighter spawn prompt on every spawn, and the write-with-reply rule at a cost nobody will dodge.

C5 · rides C1

What does prime deliberately let go — and how does it avoid re-litigating the settled?

Why now: a memory mechanism that only accretes recreates the problem it solves. The discipline of forgetting is what keeps the state file at ~1k tokens and the cold read bounded forever. And post-compaction, a prime that has lost the feeling of a settled argument will cheerfully reopen it unless the settlement is written where rehydration finds it.

C5-a · Keep everything in state

What
Append to the state file; never delete.
Costs
The state file becomes a second scratchpad on a ~week timescale; the bounded read stops being bounded; the working set drowns in its own history — which the log already keeps better.
Forecloses
The entire point of C1.

C5-b · Bounded working set, delete-on-resolverecommended

What
Four rules. (1) Answered questions are gone once relayed — the transcript keeps them verbatim, a delegate can mine it. (2) A delegate's report reduces to one pointer line (artifact URL / issue number) the moment it is relayed; the artifact is the authority. (3) GitHub state is never copied into the state file beyond a pointer — gh-sweep.json and one bounded gh call are the authorities; copied state is born stale and reads as confident. (4) A settled decision is one ## Settled line with provenance ("hub-commit inspection: Jeremy chose inspect-then-push — log 23:14") kept until applied, then deleted. Settled means cite-and-move-on, not re-argue.
Costs
Prime occasionally re-fetches something it once knew (one bounded call — the round-trip budget covers it). Deletion requires the same discipline as writing.
Forecloses
Using the state file as an archive. That is what the log, the transcripts, and the artifacts are for — three archives are enough.

C5-c · Archive sidecar

What
Move resolved lines to prime-state-archive.md instead of deleting.
Costs
Duplicates the log's job with worse provenance (no timestamps unless re-added); one more file to maintain; the archive is read by nobody until it is read by accident.
Forecloses
Nothing, which is why it is tempting — but it spends maintenance on a lane three existing mechanisms already cover.
Recommendation

C5-b — the four rules, enforced by the cap.

Letting go is what the scaffold's layering already implies: verbatim history in transcripts, narrative in the log, deliverables in artifacts, live truth on GitHub. The state file is the only layer with no archive duty, so it is the only layer allowed to forget — and it must, or the bounded read stops being bounded. The ## Settled rule is the anti-relitigation mechanism: post-compaction prime does not remember the argument, but it rehydrates the verdict with a pointer, which is all it needs to decline to reopen it.

Unblocks
A state file that is still ~1k tokens in December; settled questions that stay settled across any number of compactions.

C6 · the vehicle

Where does this land in the framework?

Why now: the mechanism touches a skill (session-prime), the canonical contract doc (session-framework.md), a template every sibling inherits, the tools directory — and, if C2-b is approved, a new agent role. Scattering it invites drift; the framework doc's own convention is that there is only ever one copy of a contract to keep current.

C6-a · Skill-only

What
Add the state contract and rehydration to session-prime's SKILL.md; change nothing else.
Costs
C4's savings never reach the other siblings (the briefing template keeps the heredoc); the framework doc stays silent on standing sessions, so the next standing agent — including the Navigator — re-derives all of this.
Forecloses
Nothing technically; practically, the ecosystem-wide half of the value.

C6-b · Skill + framework section + scripts in one PR; Navigator as a requirementrecommended

What
One obot.agent PR: (i) a "Durable state and rehydration" section in session-prime's SKILL.md — the prime-state contract with provenance stamps (C1), the lazy bundle (C3), the retention rules (C5), and the write-with-reply claims rule; (ii) a short link-only "Standing sessions" section in session-framework.md; (iii) tools/prime-rehydrate and tools/scratchpad-log, plus the briefing-template edit with heredoc fallback; (iv) /s-prime preprocessing wiring. PR left open for @jwildfire per the approval gates; the settings allowlist line ships in the PR description as his edit. The Navigator lands separately as a hub requirement issue through the normal lifecycle — it is a new agent role with scope questions of its own (the (a)/(b)/(c) boundary above), not a doc edit to smuggle into a tooling PR.
Costs
One review of a mixed docs+tools PR, plus one requirement to draft. The PR pieces are separable if he wants a subset — the body should say which chunks stand alone (C4 does; C3 needs C1).
Forecloses
Nothing; it is the reversible, reviewable shape.

C6-c · A new standalone session-state skill

What
Promote durable-state management to its own skill any session could invoke.
Costs
Over-structure today: prime is the only standing session, and working sessions have their bookends. A skill with one caller is a doc with extra steps.
Forecloses
Nothing — it can be extracted the day a second standing agent (the Navigator, say) actually exists, which is exactly when it would earn its keep.
Recommendation

C6-b — one PR for the mechanism, one requirement for the Navigator.

The skill owns the contract, the framework doc points at it in three lines, the tools make it cheap, and the template spreads C4's savings to every sibling. The Navigator gets the front door every new capability gets — a requirement with its scope boundary made explicit — rather than arriving as a side effect. Extraction into a standalone skill (C6-c) stays available the day a second standing agent exists.

Unblocks
Approving any of C1–C5 has a place to land; approving all of them lands in one review plus one requirement draft.
