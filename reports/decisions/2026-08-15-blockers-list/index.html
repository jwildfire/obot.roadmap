BL1 · What belongs on it

The test, in one sentence

Proposed rule

An item is a blocker only if the fix is fully specified and the sole missing ingredient is your physical access — keyboard, account, or device.

The counter-test catches everything else: if a one-word "yes" from you would let an agent do it, it is not a blocker — it is an approval ask or a decision. Blockers are known answers waiting on hands; decisions are unknown answers waiting on judgment; RCs are finished work waiting on review; everything else is an issue an agent can pick up.

Worked examples from the last 24 hours

  • Near-misses that look like blockers but are not: deleting an unmerged worktree and a stray branch — feels like "only Jeremy can", but an agent executes the moment he says yes → approval ask; a missing CI workflow flagged as "a precondition on him" — the workflow file was agent-writable and an agent wrote it the same night → ordinary issue; a framework-wording contradiction — nothing to type, something to decide → decision lane.
Threat model

What the list leaks, to whom, and what it actually costs

The list is, by construction, a map of the trust boundary: which settings are gated, which grants are missing, which controls have soft edges. Three adversaries, in descending order of realism:

  • A mechanical sweep — the proven one. The hub deploy workflow runs cp -r reports _site/reports and triggers on any push touching reports/**: anything placed under reports/ is on the public site within minutes, no human in the loop. A second live lane: the session wrapup folds the scratchpad into the published diary — so blockers captured in scratchpads today are already one fold away from public. The status quo is leakier than any option on this page.
  • An opportunistic reader of the public site. What they'd learn: the automation's constraint map — which files agents can't write, which tokens lack which scopes. What they could do with it: reconnaissance convenience, nothing more — the list contains no credentials, and the individually-public issue trail already discloses much of it piecemeal. The aggregation is what's new and worth withholding; this is a personal workspace, not a bank, and the proportionate response is placement and a tripwire, not encryption.
  • Your own tooling and future agents. A future agent with a broad glob, a usage-report generator, a diary fold — none malicious, all mechanical. Defences must therefore survive an agent copying the content somewhere swept, which placement alone cannot; that is what the sentinel-plus-guard below is for.
The concrete failure mode

Discipline alone fails here because the leak path is automated: one well-meaning cp into reports/, or one scratchpad fold, publishes the map with zero further human action. Every layer below assumes agents will eventually make exactly that mistake.

BL2 · Where it lives

Five homes, priced honestly

Evaluated on: who can read it, what happens on a careless git add -A, whether the deploy sweep can reach it, whether agents can append cheaply, and whether it survives machine loss.

(a) A file at the workspace root: ~/Documents/obot2/.claude/blockers.md

Recommended
Who reads
Any local agent — which is fine: agents already know the walls (they hit them); the threat is publication, not local reads.
git add -A
Structurally immune. The workspace root is not a git repository — there is no repo for any git add to run in, which is strictly stronger than a gitignore entry.
Deploy sweep
Immune by location (the workflow copies obot.roadmap/reports/ only). The copy failure mode is covered by the sentinel + guard below.
Agent append
Trivial — same directory as the session scratchpads every agent already writes; same script pattern as scratchpad-log.
Machine loss
Lost — accepted: every entry is re-derivable from its cited source (issue, artifact, close-out), and the daily count (BL4) means a vanished list is noticed, not silent. If the list ever becomes load-bearing history, option (b) is the upgrade path.

(b) A file in a private repo

Not now
Who reads
You + agents with the token; GitHub, Inc. holds the map.
git add -A
Committing is the point — but one repo-visibility flip, or one agent quoting the file into a public artifact, publishes everything at once.
Cost
No private repo exists in the portfolio today: creating one, installing the app, and teaching every agent a second remote adds real ceremony to what must be a ten-second capture. Survives machine loss — the one genuine advantage.

(c) The agent-memory directory

Wrong tool
Why not
Memories are designed to be recalled into every session's context and paraphrased into outputs — including published ones; that is the opposite of containment. Multi-writer semantics are poor, there is no check-off lifecycle, and a queue is not a memory. Tonight's sixteen-day-stale "still blocked" memory line is the standing exhibit.

(d) A file under ~/.claude/

Close second, loses on discoverability
Why not
Identical safety to (a) — outside every repo — but outside the workspace agents grep and outside the scratchpad conventions they already follow; it splits program state across two roots for zero added protection.

(e) Labelled issues in a private repo

Best surfacing, worst capture
Why not
The strongest read path (phone, notifications) and the answer to "is a separate list even right?" — considered seriously. But it needs the private repo (b)'s costs plus per-item issue ceremony, and cross-referencing public threads from private issues either leaks titles into timelines or forces agents to keep two disciplines. If BL4's read path fails in practice, this is the first alternative to revisit — the analysis says the list is right and the file form is right for v1, not forever.
Recommendation — BL2

Option (a), wrapped in four defence layers, ordered by strength: location → sentinel → deploy guard → gitignore.

1. Location: outside every repo, so no git operation and no deploy can reach it. 2. Sentinel: the file opens with a fixed local-only marker comment, so any copy of its content is self-identifying. 3. Deploy-time guard: one step in the hub's deploy workflow, after site assembly — grep -rqF "$SENTINEL" _site && exit 1, where the workflow composes the marker string from two halves rather than spelling it out, so that pages documenting the guard (this one included) can never trip it. That is the merge-gate-guard prose-false-positive lesson (oa#58) applied in advance — and not hypothetically: this artifact's own pre-push check fired on its first draft, which quoted the sentinel verbatim. 4. Belt-and-braces: a blockers* line in the hub's .gitignore for the copy-the-file case. Layers 2–3 are the ones that survive agent error, which is the failure mode that actually occurs.

BL3 · How agents write it

Ten-second capture, or it won't happen

The capture moment is mid-task, at the exact instant an agent hits a wall — any friction and the item dies in a close-out paragraph instead. The proven pattern is scratchpad-log: one allowlisted script call, shelled timestamp, append-only, multi-writer safe. Proposed:

obot.agent/tools/blocker-log '<what>' --fix '<paste-ready command or diff>' --source '<url>'
  • Entry schema: one checkbox line per item — filed-date, verified-date, what, a paste-ready fix, source link, what unblocks. The verified-date is load-bearing: the sixteen-day-stale item survived precisely because nothing forced a re-check; the read path (BL4) re-verifies before surfacing and the script stamps verification at capture.
  • Dedup: the script greps for the item before appending — tonight two of four "unfiled blockers" turned out to be already filed elsewhere; the same failure mode applies here.
  • Lifecycle: resolved items move to a Resolved section with a date — never deleted (house rule) — and near-misses get routed to their correct lane at capture time by the BL1 counter-test, which the script's help text carries.
  • A thin skill wrapper later, script first: scripts work everywhere — siblings, ultracode jobs, hooks — where skills need a session; this mirrors how scratchpad-log shipped. (Ironic footnote, logged as evidence: the script's own allowlist line will be an early entry on the list it writes to.)
BL4 · How it reaches you

The part that decides whether any of this works

Tonight's evidence is blunt: items deferred to you accumulate silently and are never surfaced again — the ones that cleared (the startup setting, the merge allowlist) cleared because a page you actually read put them in front of you, within hours. So the read path is designed around moments you are already looking, plus one deliberate sit-down mode:

  • The session dashboard (local page) gets a "🔑 Your hands" section rendering the full list — it is served locally in Chrome, never published, so full item text is safe there.
  • A /session-blockers walkthrough, modelled on session-reviews: when you give it ten minutes, it re-verifies each item live, hands you one at a time with the exact paste-ready command, and marks done / defer / retire. This is the mechanism that actually drains the list — items carry their fix, so clearing three is minutes, not research.
  • The daily briefing carries a count only — never item text. The briefing is a published page. Proposed line: "🔑 3 items need your hands (~5 min) — run /session-blockers". This is handed to the briefing design already in flight (Q&A #158, M3) as a section spec, explicitly not a competing surface; if M3 lands, the blockers count is one of its nine lines.
  • 🎩🤖 prime answers "what needs my hands?" from the file directly, and its rehydrate bundle carries the count so the answer is warm.
Recommendation — BL4

Full text on local surfaces only; published surfaces carry counts, never contents — as a hard rule, not a habit.

Adopt the dashboard section + /session-blockers walkthrough, hand the count-line spec to #158's briefing rather than building anything parallel, and treat "count-only on public pages" as the same class of rule as "no writes outside the jwildfire org".
