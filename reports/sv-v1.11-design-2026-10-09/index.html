  • Six full-page desktop mockups of the app as proposed for release 1.11, each with its changes numbered and today's page one click away.
  • Your round-one feedback is in: a slim R control that shrinks to a chip, a four-rung status ladder with one app-wide Exploratory label, an RBQM tab with status icons, capped columns and a folded log, and all data loading on the Data tab.

Decisions

Only what is still open. The recommendation comes first in each. Everything else on this page follows what you already decided: R starts on request, one presentation of R now and one shared R later, and the round-one fixes and defects stay in.

  1. Which charts carry their own label

    • RecommendedOnly a chart below the app's rung: five charts and the RBQM tab today. The label then always tells you something.
    • OrEvery chart shows its rung, so an Exploratory chart repeats the app label 80 pixels under it. Mockup 1 has the switch to see both.

  2. The words of the disclaimer

    • RecommendedOn hover: "Nothing in this app is qualified. Confirm every result." On click, the paragraph in mockup 2.
    • OrYour own words. It is a disclaimer, so the wording is yours to set; the component takes any sentence.

  3. The colours of the Biomarkers and RBQM tabs

    • RecommendedLet the rule choose: Biomarkers pink, RBQM amber. Neither module names a colour today.
    • OrName a colour for either one. It is one line in the app's list of libraries, and the rule then leaves it alone.

  4. A standard file whose name matches a raw domain

    • RecommendedOn the Data tab a file is a gsm raw file only when its name starts with "Raw_" or its columns match exactly one raw domain. A standard file called ae.csv stays a standard file.
    • OrKeep the RBQM tab's rule of today, where the name alone decides. That would turn the ae.csv of the "Renamed columns" demo study into a raw file and break that study.

  5. The reason shown for each Experimental label

    • RecommendedShip the six sentences listed under Status ladder. One is already on the docs site; five are my drafts for you to correct.
    • OrLeave a reason empty: the panel then shows only what Experimental means.

The mockups

  • Each is the whole app page at 1,280 pixels wide, scaled to fit this column. "Full size" shows it at true size, scrolling inside its frame.
  • The header, tabs, rows and footer are built from the app's own styles at release 1.10. Where a chart goes there is a still of the real chart, captured from the live app on 9 October 2026.
  • Numbers on a mockup match the list under it. "Today" swaps in a capture of the released page in the same state.
  • Labels, the R control, the run button and the log all work on click.
What a first-time visitor meets today
  • Nothing says whose data is on screen, how many charts there are, or how far to trust a result. Mockup 1.
  • Two of the six tabs are graphite and read as switched off; the wordmark is not a link; a tab's "9 of 9" has to be worked out. Mockup 1.
  • Starting R is explained by a long sentence inside the chart, and nothing shows it is ready except a greyed button. Mockup 3.
  • The RBQM tab opens on a paragraph, a file box and an empty page, and ends in a log that outweighs the results. Mockups 4 and 5.
  • Choosing the RBQM demo study leaves every chart tab hollow and the Data tab reading "0 of 18 charts ready", with nothing pointing at RBQM. Mockup 6.

Status ladder

  • Four rungs, highest first: Qualified, Exploratory, Experimental, Prototype. Nothing is Qualified.
  • The app's rung is Exploratory, and so is every chart that says nothing else: 13 of the 18 charts.
  • Experimental: five charts and the RBQM tab. Prototype: the Patient Journey Explorer, on the docs site only.
  • The glyph is four bars, filled up to the rung, so the label can be read without its word: Qualified, Exploratory, Experimental, Prototype.
  • No pile-up: one app label, and at most one more on the open view.
  • Where the header has no room for the word, the app label shrinks to its bars. The word stays in its name for a screen reader and comes back on hover.

How the rung is stored

  • Today, in the site configuration: every chart has status: "available" or "planned", and a chart below stable adds experimental: true or prototype: true. The RBQM tab has the same flag in the list of app tabs.
  • Proposed: one field, tier, with one of qualified, exploratory, experimental, prototype, and an optional tierNote for the one-sentence reason. Both on a chart and on an app tab.
  • The default when tier is absent is exploratory. So the 13 unlabelled charts need no edit, and six entries change a flag into a field.
  • status stays as it is: it says whether a chart exists yet, which is a different question.
  • The build stops with a sentence if any entry says qualified, until there is a qualification record for it to point at.
  • The app does not know a chart's rung today; only the docs site reads the flags. The app build has to hand the rung and its note to the page with each chart.
  • A chart from another library is Exploratory unless that library's own list says otherwise, by the same field.

Tab colours

  • A module that names a colour for its tab gets that colour. Its chart names and file cards use it too.
  • A module that names none gets the first open colour from a fixed list: pink, then amber, then green. Open means no tab in the header uses it.
  • Modules are taken in the order the app's build lists them, which never changes between loads. So the same module has the same colour on every load, and a module added later goes to the end and moves nobody.
  • Red is never given out. It means "missing" and "did not draw" everywhere in the app.
  • When the list runs out, the app goes round again with each colour mixed 40 percent toward ink: a darker pink, a darker amber, and so on. Never grey.
  • Today, with no module naming a colour: Biomarkers is pink, RBQM is amber.
  • Labs and vitals, blue
  • ECG, violet
  • Adverse events, teal

Why the labels are not coloured

The status labels are ink on white, and the rung is read from the bars. A coloured Experimental label beside an amber RBQM hex would look like the same signal.

Metric status icons

  • RanA filled green hex with a tick. Read aloud and on hover as "Adverse Event Rate: ran".
  • Did not runA grey outlined hex with a bar. On hover, R's own sentence: "… needs Raw_PD.csv, which is not loaded." Grey, because missing data is not an error.
  • RunningA turning ring in the app's plum, still when the reader asks for reduced motion. "Adverse Event Rate: running".
  • Not startedA dashed outlined hex. "Adverse Event Rate: not started".
  • The icon is decoration to a screen reader; the button's name carries the metric and its state in words.
  • A short key sits under the buttons, listing only the states on screen.
  • The same icons are used on the Data tab's RBQM card, so the two tabs say the same thing the same way.

Data loading: what moves to the Data tab, in the code

Already shared

  • The app, not the RBQM tab, already holds the raw files: its state has a list for them, and a loader that keeps a file as it is with its column names and row count (src/app/page.js, lines 234 and 806 to 834).
  • The Data tab already shows them: a card per raw file, a row in "Loaded data", and "Nothing to map" at step two (src/app/data-panel.js, lines 252 to 267, 386 to 388 and 445 to 455).
  • The RBQM demo study already arrives through the Data tab's study menu and that loader.
  • Reading files from disk is one function used by both tabs (readFiles, src/app/data-panel.js, lines 32 to 53).
  • Everything that decides what a file is and what the data supports is one module with no page code in it: placing a file in a raw domain, the study of raw files, the standard files R can stand in for them, and which metrics all of it supports (src/app/rbqm-files.js). It moves nowhere.

What has to move or change

  • Routing. The Data tab's drop zone sends every file to the standard loader. It has to ask first whether the file is a raw file and send it to the other loader. This is the one real change in behaviour.
  • What the workflows need. The list that says what each raw domain and each metric needs is handed only to the RBQM tab today. The Data tab needs it too. The clean way is for a tab to be able to say "these files are mine, and here is what the loaded data supports", so the Data tab asks the RBQM tab and holds no RBQM knowledge of its own.
  • The lists. "Loaded files", "From the loaded study" and "What they support" are drawn on the RBQM tab (src/app/rbqm-view.js, lines 546 to 596). They are drawn on the Data tab instead. The sentences are unchanged.
  • The RBQM tab's drop zone and file box are removed (same file, lines 496 to 545), and the tab keeps one line with a link.
  • A CSV-only rule: raw files are CSV, and the RBQM tab refuses others with a sentence. The Data tab also takes JSON, so the rule and its sentence move with the routing.

Size

  • Code: medium. About 100 lines leave the RBQM tab, and about as many arrive on the Data tab, plus a short routing rule.
  • Tests: the larger half. The unit tests of the RBQM tab mention the file box on 32 lines. In the browser tests, two long cases cover a reader's own files on that tab and several more read its lists. They are rewritten for the Data tab, with the requirement rows they prove.

Risks to what RBQM does today

The one to design for

The RBQM tab places a file by its name before its columns, so "ae.csv" is the adverse events raw file whatever is in it. That is safe on a tab where every file is meant to be raw. On a shared drop zone it would claim the standard ae.csv of the "Renamed columns" demo study. Decision 4 is the stricter rule that avoids this.

  • The reverse fault exists today and this change fixes it. Dropped on the Data tab of release 1.10, Raw_SUBJ.csv is read as the Subject-level file and Raw_AE.csv as the Adverse events file, and the RBQM tab then reads "0 of 8". Mockup 6 shows it under Today.
  • A reader's own files clear a loaded demo study, in both loaders. A drop that mixes raw and standard files must clear it once, not twice, and say so once.
  • Raw files and a standard study loaded together already work: a raw file wins over the table R would make from a standard file. The routing must not change that order.
  • The sentences are held, word for word, to what desktop R says of the same files by a unit test. Moving where they are drawn does not touch that test; rewording them would.
  • The single-file download of the app, which loads nothing, keeps its sentence that RBQM needs R. Nothing here changes it.

What I could not verify

  • The R version in the ready chip on the Biomarkers tab. The RBQM tab already reports it; whether the biomarker library's R engine can be asked for it without a release of that library is not checked.
  • The column rule on the real table. The mockup's table is my own markup with the app's styles; the live table is drawn by gsm.viz. Its cells carry no widths of their own in the capture, so the same two style rules should hold, but it is not tried on the live table.
  • Five of the six Experimental reasons are my drafts, not statements from the repository.
  • The per-step times in Run details are from one run on 9 October, read from the status line once a second.
  • Nothing here was tried at phone width as a design. The mockups are desktop only, as asked; the phone fixes in the change list are carried from round one.
