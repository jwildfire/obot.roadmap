What is wrong with the page today

Not the content — the format. Every finding is a card carrying its own copy of the rule's reasoning, so the page is written for a first read and paid for on every read after that.

Measured in Chrome at 1480 × 812 on the deployed page and on Option A with the same 33 findings. The live page also carries 2,883 words and 77 buttons before you have decided anything.

The deeper problem is repetition. Ten of the thirteen rules that fired propose the same change for every finding they produce — eight identical "Assign @jwildfire", three identical "Set board Status to Released". The page asks the question 33 times when there are really 13 questions and a handful of exceptions.

  • A rule band with ✓ / ✗ for all of it. Rules group the table; the band decides every finding under it in one click, and reports 3/8 decided when you have only touched some.
  • A collapsible sidebar carrying search, sorts (confidence, rule, issue, age, runs, kind), facets for confidence / kind / rule group / repository / decided-state, and three saved sweeps — the useful one being high confidence, mechanical, undecided, which is the batch you can clear without reading.
  • Staged decisions and one Apply — superseded by D2. In the prototypes nothing dispatches: the tray counts what is staged and Apply prints the exact repository_dispatch body. The shipped view fires each click instead; the tray comes out.
  • A queue meter above the table: one tick per finding in table order, filled as you decide, hover to identify, click to jump. Progress and minimap in the same object.
  • Keyboard triage. j/k move, a accept, x reject, u undo, enter details, / search. Deciding advances to the next row, so a clean sweep is a a a x a.

What I recommended

Kept for the record. D1 went to B on its own rather than as a toggle on A.

Option A, with B's rail as a toggle rather than a rival. A and B are the same build — the same table, the same bands, the same sidebar — differing only in whether detail renders under the row or beside it. That is a preference, not an architecture, so it should be a control on the page and not a decision made once for you. Default to the rail on a wide screen, because 15 of 33 findings are judgment calls that need a paragraph read before they are decidable, and fall back to inline expansion below 76rem where the rail does not fit.

Take one idea from C immediately. When every finding under a rule proposes the identical change — ten of thirteen rules today — the band should say so once: all 8 · Assign @jwildfire. That single line is where most of the remaining reading disappears, and it turns the band's ✓ from a bulk action into an informed one.

Do not ship C first. Its wizard is genuinely faster on a queue like tonight's, but it hides the queue: you cannot see that 13 high-confidence findings are one click away, and a rule you never step to is a rule you never decide. Worth revisiting once the compact view has been lived with for a week — it is a mode, not a replacement.

What this means for PR #110

The backend survives intact: repository_dispatch, the re-validation against a fresh audit, the ledger, the run polling. What changes is only the surface calling it: the card list becomes Option B’s table and rail, the accept and reject buttons move onto the row and the rule band, and the run reporting the PR already built stays as it is (D7). The connect-once token flow is untouched. D2 kept per-click dispatch, so the tray and its payload preview — the one behaviour these prototypes have that the shipped view will not — come out; a rule band sends a single request carrying all of its finding ids, which the lane already accepts.

What is not in the prototypes

  • Nothing reaches GitHub. No token, no dispatch, no run polling — Apply prints the request body it would send.
  • The data is a snapshot of site/audit/findings.json as committed at 09:16 UTC on 2026-07-25, so the three options stay comparable while the nightly moves on.
  • Light theme only, matching the site. Every colour is a token and no component hard-codes white or black, so a dark block can be added without touching a component.
  • The activity log is not rendered — see D4. Prior decisions on a finding do appear in its detail, from the real decisions.json.
  • Small screens are roughed in, not designed. The rail and the sidebar collapse; the table itself still wants width.
