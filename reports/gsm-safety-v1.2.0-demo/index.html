part 1 · the widget parity work · measured again 2026-11-11

The liver chart stops reading a baseline as a peak

gsm.safety's composite liver view had been reading some participants' own baseline as if it were an on-treatment peak. This part swaps the chart library under every widget from safety.viz v1.4.0, which gsm.safety v1.1.0 ships, to v1.12.0, where the rule is corrected. It adds two charts that had no R binding at all and puts a parity guard in CI. The comparison below was run again on 2026-11-11, on the example data this release ships: both bundles, the same data, the same widget code.

sv#91 · the clinical change

The same chart, drawn by the old bundle and the new one

Both captures below come from one report file, built from the release's own hep-explorer workflow. The widget code, the settings and all 57,929 rows of the example data are byte-identical between them; the two copies differ only in which safety.viz.js they load. Read the panel titles in the lower row: each counts the participants whose on-treatment peak falls in that quadrant.

What the difference is

  • The old rule: the baseline is the day-zero record, or else the earliest; on-treatment is every record after day zero.
  • ADaM numbers the day of first dose as day 1, and there is no day zero. A baseline drawn on the day of first dose sits on day 1, so the old rule put the baseline record in the on-treatment set too. The participant's own starting value could then be reported as their peak, and their peak could never come out below baseline.
  • The new rule: the baseline is the record the data flag as baseline (ABLFL, which the release's workflow names), or else day zero, or else the earliest. On-treatment is every other record after both day zero and the baseline's own day.

Why it matters

eDISH is read by eye. A point that sits at its own baseline is indistinguishable from a point that genuinely peaked there, and a participant who improved on treatment could not be drawn below the diagonal at all. On this data, 15 participants would be drawn in Hy's Law by the old rule only because their baseline, taken on day 1, was their highest value.

A baseline on the day of first dose is ordinary in ADaM data. The same corrected rule feeds the migration view and the ALT waterfall. The plain eDISH scatter uses a different per-record path and is unaffected.

The safety census rebuilt on metrics

A safety overview leads with denominators: how many participants, how many dosed, how many died. gsm.safety computed those inside one function, from whatever columns it was handed, and got several of them wrong. This part replaces every one with a metric that publishes its own numerator, its own denominator and a record of where the figure came from, adds the report that reads them, and keeps SafetyCensus() by name with its arithmetic moved out. Both versions were run for this update on 2026-11-11, on the same study, in the same session: the released v1.1.0 and the candidate.

gs#61 · the page it produces

The census report, rendered

One report, reading what the metrics published and computing nothing of its own. Rendered for this update from the release candidate's code by running the whole pipeline: the standard mapping, the eleven census metrics with a domain on this study, the reporting model, then the report workflow.

Why it matters

A figure that is wrong is now wrong in exactly one place. Before, the same count could be produced by a function and by a metric and the two could disagree without anything noticing. Now the function runs the metrics and reads what they published, so there is one counting lane and the page is a reader of it.

The test that proves it is not the one that checks the numbers. A structural check reads the function's body and every helper it calls, and fails if an arithmetic operator or an aggregating function appears in any of them. A rebuild that left the counting in place and put a workflow beside it would pass an arithmetic test by accident; it cannot pass that one.

Three states, kept apart, and checked in the strongest form available

  • Every column every census definition declares is dropped in turn, and the metric has to stop rather than publish: 34 combinations across the eleven metrics, plus four for the death count.
  • This matters because the underlying check only warns on a missing column: it stops on a missing data frame, but a domain arriving without a column it needs would otherwise sail through. That was verified on gsm.core 1.3.1 when the work landed rather than taken from the design, which had called the false-zero problem fixed by construction.
  • The ECG metric is written, declares its domain, and stops on every study available today: no mapping package ships an ECG mapping and the bundled study has no ECG records. Its qualification is structural rather than measured, and the suite fails if a bundled ECG domain ever appears, so it cannot sit there passing on nothing.

On a study that maps no death domain, the death figure now reads as not collected instead of reading a discontinuation reason. That is correct, and it is also a visible change: the demo study's deaths and randomised tiles will read as not collected until its mapping phase adds those two domains.

part 3 · the last two widgets · never a candidate of its own, merged to dev 2026-08-27

Every chart safety.viz draws can now be drawn from R

The two renderers part 1 left on the deferral list ship here: the Kaplan-Meier time-to-event display and the participant profile. Both were held back by the same thing, and it was never the JavaScript: each needs a second data frame, and the widget contract carried one. The contract is now general. A widget reads the datasets its module's data contract names rather than assuming there is one, and the eleven existing widgets return byte-for-byte the payload they returned before. The deferral list in .github/parity-allowlist.yaml is empty, and a test asserts it equal to the suite's own list so the two can no longer disagree.

What each widget takes and draws, from the release notes and the merged pull request (gsm.safety#72, closing gsm.safety#71).

Widget_TimeToEvent(dfResults, dfPopulation, ...)

  • Two frames: the events, and the population that is the denominator.
  • Kaplan-Meier curves for an endpoint composed while looking at it: multiselect filters over the adverse events decide which events qualify; each participant's first qualifying event counts; everyone else is censored at their own follow-up-end day.
  • Greenwood log-log pointwise 95% bands, censor marks, the at-risk and cumulative-event tables under the axis. Cumulative incidence is the default orientation; survival is a control away.

Widget_ParticipantProfile(dfResults, chrParticipants, dfAE, ...)

  • One frame plus an optional adverse-event frame; the cohort is an argument.
  • The drill-down as a report of its own: a demographics header, labs over time standardised to multiples of the upper limit of normal or of baseline, adverse-event tracks on the same study-day axis, a measure table whose sparklines expand into an inset.
  • A cohort of more than one is ranked worst-first and stepped through. Without chrParticipants the profile waits for a selection a static report never sends.
  • Its axis can now be the visit or the real study day; part 5 shows it.

ExampleData("adsl")

  • One row per participant with treatment arm, follow-up-end study day and end-of-study status: the population denominator the time-to-event widget censors against, vendored byte-identical from the safety.viz demo data.

Proven by what they painted, not by a file existing

A widget that loads nothing looks exactly like one that works: a binding that constructs its renderer and never hands it data raises no console error, still emits its element, still ships the bundle and still carries every data value in the page. Both widgets were opened in headless Chromium when the work landed on 27 August, with the 1.7.0 bundle, and measured: 95,478 painted pixels for the curves and 19,717 for the profile, against 0 for a deliberately broken control that no assertion in the suite could tell apart from the real one. Those pixel counts were not measured again for this update. A new test now asserts that every binding both constructs and feeds its module, proven red with the feed call removed and green with it restored, and it runs on every change.

Two things this part settles that were open

  • The design question the participant profile was waiting on turned out to be two-thirds already answered by the vendored bundle: the compound widget hosting a chart plus a rail cannot be built from R because safety.viz does not export profileRail on its public object, and the profile-enabled lab widgets already shipped in part 1 (Widget_HepExplorer(), Widget_Histogram() and Widget_OutlierExplorer() mount the rail from their profile setting). The standalone surface was the only real gap, and it is what this part adds.
  • Five workflows had been failing before they started, two of them the qualification checks. The upstream templates moved organisation on 4 August; GitHub redirects an action called from a step but not a reusable workflow called from a job, so pkgdown-all, test-coverage, qcthat and workflow-template-check had failed every run since with zero jobs and raised no check run, and the release workflow failed the same way on v1.1.0, which published with no artifacts. Every workflow file is now the current upstream template (gsm.safety#73), so this release publishes its artifacts and its pull request shows every check.

Marked experimental, on purpose

When @jwildfire approved safety.viz v1.7.0 he kept its time-to-event chart marked experimental until an external review confirms the Kaplan-Meier implementation. A chart marked experimental in the library and unmarked in its R wrapper would be the same wrong-confidence problem on a different surface, so the R widget carries the marking too until that review completes (the un-marking is filed as obot.roadmap#182).

part 4 · the FDA guide's thresholds · was the v1.5.0 candidate, measured 2026-09-11

The FDA safety guide's rules, in R once

The FDA's Standard Safety Tables and Figures guide is mostly rules rather than drawings: three levels of laboratory abnormality, values so extreme they are treated as errors, results read as multiples of the upper limit of normal. Nothing in R carried those rules. This part is the foundation the static figures will stand on: the guide's appendix tables as package data, the first three functions that apply them to a lab table and hand the table back with the answers added, a requirement matrix that keys every one of the guide's 22 figures, and a column-by-column check of what the demo data can draw. Every number was produced from dev on 2026-09-11; the row counts and the grading table were run again on the release candidate on 2026-11-11 and did not move.

part 5 · the study day · new in this update, measured 2026-11-11

Visit or study day, chosen from R

Every safety.viz chart that shows change over time carries a Visit | Study day toggle, raised by a member of the working group. This release carries it into R, and fixes what the study day meant in the package's own examples.

  • Four widgets take the toggle as x_axis in lSettings: the participant profile, hep-explorer, the outlier explorer and the QT explorer. Each documents it and has an example that sets it, and their report workflows pass it.
  • The study day is now DY, the ADaM study day, never the visit number. The example data (ExampleData("adbds"), "adbds_abnbl" and "adeg") carry DY and the baseline flag ABLFL beside each visit. In v1.1.0 the hep-explorer workflow passed the visit number as the study day.
  • The hep-explorer workflow opens on Study day; the participant profile, outlier explorer and QT explorer workflows open on Visit. The hep waterfall takes no toggle: its contract (inst/schema/hep-waterfall.json) has no x_axis. What changed for it is its studyday_col, now DY instead of VISITNUM.
  • The profile, hep-explorer and hep waterfall workflows read the baseline from the flag (baseline_col: ABLFL) rather than taking the earliest record.

What the visit axis could not show

  • 01-701-1028 has two adverse events: application site erythema from day 3 and application site pruritus from day 21.
  • On the visit axis, day 21 has no place: Week 2 is day 14 and Week 4 is day 27, drawn one step apart.
  • On the study-day axis, the pruritus begins a week after the Week 2 labs and six days before the Week 4 labs, and the timeline under the chart shares the chart's axis.
  • The release's tests check this exact case: in the profile report's Study day view, this participant's day-21 event sits between the Week 2 and Week 4 labs.

Why it matters

A visit number is a label, not a time. Plotting it as a day spaces Week 2 and Week 4 as far apart as Week 24 and Week 26, and gives an adverse event nowhere to sit between visits. A reviewer reading an event against a lab change needs both on the same clock.

The same fix is what changed the eDISH comparison in part 1: with the real study day, a baseline taken on the day of first dose is on day 1, which is exactly where the old liver rule went wrong.

  • Two new widgets — Widget_HepWaterfall() and Widget_NepExplorer() — the hepatic ALT waterfall for abnormal-baseline trials (Amirzadegan et al. 2025, Fig. 5) and the KDIGO nephrotoxicity explorer, each with its report workflow, example page, and bundled demo cohort (adbds_abnbl; synthetic AKI-* participants join adbds).   • Widget_TimeToEvent() — Kaplan-Meier curves for an endpoint you compose while looking at it. The module takes each participant's first qualifying event, censors everyone else at their own follow-up-end day, and draws the product-limit estimator with Greenwood log-log pointwise 95% bands, censor marks, and the at-risk and cumulative-event tables beneath the axis. The census rebuild

Twelve of the thirteen census metrics, and every clinical figure the safety overview leads with is now a number the pipeline computes, publishes beside its denominator and can be checked on its own, or is named as absent where the study maps no domain behind it — plus the report that reads them, and SafetyCensus() rebuilt on top of both. All four steps of the SafetyCensus rebuild (obot.roadmap#274, design D0023 approved 2026-08-20).

The published figures move in this release, and that is the release rather than a footnote to it. A safety tool that quietly corrected a death count would be worse than one that never had the bug, so every figure that moved is named above with what it was wrong about, and every figure that left the payload is named with why nothing publishes it yet.

The death count came first because it is the number the review was written about. The other eleven follow it into the same machinery: the same declared columns, the same guard, the same anchor to the enrolled population, and the same empty flag. Four of them report a different number than SafetyCensus() does today, and each of the four was wrong for a reason named above.

Data completeness, the thirteenth, is not here. Why is under Worth knowing about the census.

The report is the third step, and its whole job is to read. It presents the figures the metrics published, beside the denominators the metrics published, under the labels the metric definitions carry — and it computes nothing of its own, so there is no second counting lane and no way for the census to disagree with the rest of the package about the same study. What each metric published is printed verbatim at the foot of the page, so every presentation on it can be checked against its source without leaving the page.

What left the payload, and why nothing publishes it yet

SafetyCensus() computes nothing now, so a figure no metric publishes is not in what it returns. Three things a caller saw before this release are gone, and none of them is gone quietly.

What left Where it went Why it is not computed here
Median days on treatment nowhere yet — it wants an averaging step in the metric layer (#61) a median computed beside the metrics is a second counting lane whatever table it is computed from, and the second lane is the defect this rebuild exists to remove
The per-visit data-coverage table carried to the thirteenth census metric (#58) gsm.mapping's lab domain carries no visit column under the standard mapping, and the expected count needs a per-visit study day no domain supplies. Disposition now holds the three states the disposition metrics publish: completed, discontinued and died

And one figure is absent rather than wrong wherever a study does not map the domain behind it. A study with no death domain now reads as not collected for deaths instead of reading a discontinuation reason, with a warning naming Mapped_Death. That is the intended behaviour and it has a consequence worth stating plainly: the DEMO-301 demo site's study maps no death domain and no randomisation domain today, so its deaths tile and its randomised tile read as not collected until its mapping phase adds them (the bundled qualification study maps both, and reports 12 and 567). Absent is not zero, and it is not a quiet blank either — the pipeline log names the domain that would have produced each figure.

What's new in the census

  • saf0004, a descriptive study-level death count (#56) — counted from Mapped_Death, which is gsm.mapping's own union of the death domain and the discontinuation reason, so no clinical definition of death is written in this package. The metric declares every column it reads, counts each participant once however many rows the domain carries for them, and anchors the count to the enrolled population.

  • The metric does not flag, and cannot (#56) — no threshold in its meta, no flagging step in its workflow, nothing amber and nothing red (D0023.3). New exported step Flag_None() stands where gsm.core::Flag() would and leaves the flag empty, following gsm.kri's srs0001 site risk score, which has published its rows that way in production throughout. Empty, not zero: a zero would mean measured and found fine. Because the metric carries no threshold it contributes no weights, so gsm.kri's risk-score builder skips it and this figure cannot move a site's risk score.

  • New exported step Input_Deaths() (#56) — the numerator behind saf0004, and where the three states are kept apart: a study with no death domain, or a death domain missing a declared column, errors; a death domain with no rows at all publishes no figure and warns; a populated death domain marking nobody as died publishes zero. Absent is not empty and empty is not zero — only the last of the three is a measurement.

  • Study level is a setting, not a rewrite (#56) — GroupLevel and GroupCol are meta values the workflow reads, so moving the metric to site or country level is two lines rather than a second definition (D0023.4).

  • Eleven more descriptive census metrics, saf0005 through saf0015 (#58) — enrolled participants, randomised participants, participants dosed, participant-days on study, participant-days on treatment, participants with a lab result, with an ECG, with a reported adverse event, with a disposition record, who completed, and who discontinued. Each declares the exact columns it reads, each carries the same guard, and none of them flags.

  • Two new exported steps behind them, Input_Participants() and Input_ParticipantDays() (#58) — one counts the participants a domain names, optionally only those whose column matches a value or records anything at all; the other sums a person-time column. Eleven metrics share two steps on purpose: eleven hand-written counting functions are eleven chances to leave out one of the rules, which is the defect class this rebuild exists to remove. The differences between the metrics — which domain, which column, which value — are declared in the definitions, where a reader can check them.

  • Every count is anchored, deduplicated and guarded, and the tests say so for all eleven at once (#58) — one table drives the workflow suite, so every metric is asserted to publish no row when its domain is empty, to be unchanged by a duplicated row, and to ignore a participant identifier that was never enrolled. The column guard is checked in its strongest form: every column every definition declares is dropped in turn, and the metric has to stop. A column a definition declares but no step reads would be a promise to a reader that nothing keeps, and this is what makes that impossible to leave behind.

  • Participant-days are published as days (#58) — the number actually summed, in the unit the subject domain records. The report presents years and does the division, so the metric stays checkable against the domain it came from. Person-time that was never recorded leaves the total and the denominator together, with a warning naming the participants: missing days are not zero days.

  • Dosing is a recorded first dose (#58) — saf0007 counts participants with a firstdosedate, not participants whose treatment duration is greater than zero. On the bundled study that is 80 more participants (599 to 679), every one of them with a first-dose date and no time on treatment. re-measured 2026-11-11

  • Randomisation is counted from the randomisation domain (#58) — saf0006 counts that a participant was randomised without reading what they were randomised to, so the figure stops depending on a treatment-arm column a blinded safety view should not read anyway (and which no standard domain carries).

  • The census report, inst/workflow/4_modules/safety_census.yaml (#61) — one report workflow over the census metrics, modelled on the gsm.kri report: the workflow declares the reporting tables it reads and its steps call helper functions, rather than one large function doing the work. It renders a self-contained HTML page — the study's population, its exposure and its follow-up, each figure beside its own denominator — from Reporting_Results and Reporting_Metrics alone.

  • Four new exported steps, and none of them counts anything (#61) — Report_CensusFigures() lays the published figures out in the sections the workflow declares, Report_CensusCoverage() reads a data-coverage metric's rows, Report_CensusProvenance() records what every metric published verbatim, and Report_SafetyCensus() writes the page. None of them takes a study domain as an argument, so none of them could recount a figure even by accident — which is the property the whole rebuild rests on, and the tests check it by feeding the report figures that are deliberately not the study's, and requiring the page to show them.

  • The report presents years and the metrics publish days (#61) — the two person-time metrics are named in the workflow's own settings, along with the days to a year, so the division is a declared presentation rather than a decision buried in code. Both numbers reach the reader: 27,186 participant-days on study appear as 74.4 person-years in the exposure table and as 27,186 in the provenance table below it. re-measured 2026-11-11

  • Nothing on the page flags (#61) — no flag column, no colour carrying a verdict, no cut-point (D0023.3). A result that arrives carrying a flag is refused rather than presented, because a page that shows no flags would hide a signal rather than describe a study.

  • A metric that published nothing is named, not blanked (#61) — the provenance table keeps three states apart: a figure that was published (including a published zero, which is a measurement), a metric that ran and published no row, and a metric this study never ran. On the bundled study that last one is the ECG count, which stops on the missing domain rather than reporting a zero. A blank cell in a census table is the defect this replaces; a line saying which metric produced no figure is not.

  • SafetyCensus() keeps its name and loses its arithmetic (#66) — the function runs the census metrics over the domains it is given and reads what they published through the report's own helpers. Every number it returns is a Numerator a metric published, beside the Denominator that same metric published. There is one counting lane in this package now, and it is the metric; a figure that is wrong is wrong in exactly one place.

  • Two new domain arguments, dfDeath and dfRandomization (#66) — the death count reads gsm.mapping's Mapped_Death, which is its own union of the death domain and the study-completion domain's discontinuation reason, and the randomised count reads Mapped_Randomization rather than a treatment-arm column a blinded safety view should not read. Both are appended after the released arguments, so a positional call keeps its meaning.

  • The column arguments are deprecated and ignored, not removed (#66, D0023.5 approved) — strArmCol, strTimeOnStudyCol, strTimeOnTreatmentCol, strLabVisitCol, strLabVisitNumCol, strECGVisitCol, strECGVisitNumCol, strCompleteCol, strReasonCol and chrDeathValues still exist and passing one still runs; it warns, names what it named, and changes no figure. Every census metric declares the columns it reads in its own definition, so the function no longer takes a column name from its caller.

  • strIDCol still works, and strGroupCol is new (#66) — a domain keyed on another participant column is renamed to the mapped-domain convention before the metrics read it. A subject domain with no study identifier still counts, with a warning: the identifier groups the metrics and never appears in what the function returns, so refusing to count without one would break a caller over a value it does not publish.

  • A test the rebuild can fail (#66) — the fixtures behind SafetyCensus()'s suite are built so that the arithmetic the function used to do and the arithmetic the metrics do give different answers, and the tests assert the metric's answer. Beside them, a structural check reads the function's own body and every helper it calls and fails if an arithmetic operator or an aggregating function is named in any of them. A rebuild that left the counting in place and put a workflow beside it would pass the first kind by accident of agreement; it cannot pass the second.

  • The qualification records ship inside the package (#63) — the three records behind this release moved from design/ to inst/qualification/, so they travel with the thing they qualify. A reviewer reaches them from the installed package with system.file("qualification", package = "gsm.safety"), without the repository — and, the reason it matters most here, the checks that read them now run under R CMD check, which is the context the merge is gated on. design/ is .Rbuildignore'd and absent from the built tarball, so those checks used to skip in exactly the place that decides whether the work lands.

  • Every qualification record is checked against the code, and the records against each other (#63) — death-count-qualification.md and census-metrics-qualification.md had no document-agreement layer at all, and the report's own record was not checked by the file that checks the other two. All three are now: every figure in every table of every record is compared with the constants the suite asserts against the live pipeline, and a disagreement fails by name — census-metrics-qualification.md records saf0013 route A: 77, expected 76 — instead of staying green. That is not hypothetical. The death record carried a wrong SafetyCensus() figure for a day and a person reading it caught it, not a test; that figure is now checked in both records, which have to agree with each other about it.

Worth knowing about the census

  • The bundled study moves, so the qualification is version-pinned. The reference study has changed under the same name twice: enrolled went from 760 (gsm.core 1.2.0) to 762 (1.3.1) to 754 (1.3.2), and the published death count from 12 to 13 to 12. The qualification test always checks the identities that hold on any version — that the two routes agree, that the count is the union anchored to the enrolled population, that it exceeds what the replaced function reports — and pins the exact counts to the gsm.core version they were measured on, now 1.3.2. A different version skips those assertions with the recorded and the live numbers both named. Re-qualifying a clinical count is a deliberate act, not a silent re-derivation.

  • gsm.core::CheckSpec() only warns on a missing column. The design assumed a declared column that is missing would stop the workflow with an error, and called the false-zero defect fixed by construction. It errors on a missing data.frame but merely warns on a missing column — verified again against gsm.core 1.3.1. Declaring the columns is therefore necessary but not sufficient. Every census metric in this release checks its own columns and stops, through one shared guard rather than twelve copies of it.

  • Data completeness is not in this release, and that is a scope call rather than an oversight. It is the one census figure whose inputs the design leaves open — "a declared input rather than an assumption" — and scoping it turned up two facts that have to be settled before it can be written. Mapped_LB under the standard mapping carries no visit column at all, and a metric's own Mapped_* spec does not propagate back into Ingest()'s column subsetting, so a coverage figure cannot key on a lab row's visit label even if it wanted to. And with "expected" answered as the participants whose time on study reaches a visit (D0023.2), the expected count needs a per-visit study day that neither Mapped_VISIT nor Mapped_SUBJ supplies. Both are definitional choices that belong with the coverage table in the report step, not guesses made here. Recorded in inst/qualification/census-metrics-qualification.md.

  • saf0011 is written but cannot be measured on any study available today. gsm.mapping ships no ECG mapping and the bundled study has no ECG records, so the ECG count has no second route to be checked against. What is checked is that it stops rather than publishing a zero when the domain is absent — the designed behaviour — and the suite asserts that no bundled ECG domain has appeared, so if one ever does the test fails and the metric gets measured rather than left passing.

  • On the bundled study, dosing and enrolment now differ. On gsm.core 1.3.1 firstdosedate matched enrolldt for every enrolled participant, so saf0007 and saf0005 both read 762 and the study did not exercise the fix. On 1.3.2 they read 679 and 754, so the two can be told apart on the reference study.

The index now carries all of them, under a Metric steps section that says which metrics each step feeds and a Study census section that says the function is unchanged until step four. Verified by building the index locally, which now succeeds.

Three of its figures did not survive re-measurement on 1.3.1, and one of step one's did not either: SafetyCensus() reports four deaths on this study, not one. All of them are recorded in inst/qualification/census-metrics-qualification.md with what changed and why.

  • Data coverage is absent from the report, and absent is not empty. The thirteenth metric did not land, so no study supplies a coverage figure today and the report renders without a coverage section rather than with an empty coverage table. That is the point: an empty coverage table would read as a study with no data rather than as a report with no metric, which is the exact confusion a coverage figure exists to prevent. The workflow's settings name the coverage metric IDs to read and ship naming none, so the section appears the day a coverage metric does — checked in the suite from both directions.

  • Two things D0023 placed in the report are not in it, on purpose. The design says the report would compute the median days on treatment from the exposure metric's per-participant table, and would build the breakdown of discontinuation reasons from free text. #61 sets a harder bar than the design did — a number no metric produces is a missing metric, not a calculation to put in the report — and the bar wins, because a median computed in the report is a second counting lane whatever it is computed from. Neither figure is lost: the median wants an averaging step and the reason breakdown wants an enumeration the metric layer cannot express, and both are named here rather than quietly dropped. The blank-reason defect they were meant to fix was not fixed in step four either: it was removed with the free-text reason breakdown that carried it, which is under What left the payload above.

  • Two figures deliberately carry no denominator, because their reader turns one into a percentage. Every census metric publishes a denominator and the report shows it in a labelled column. This payload has no such column: 74.4 person-years of 754 (10%) is what carrying it through would produce. So the enrolled count and the two person-time figures carry none, exactly as before, and every other figure carries the denominator its own metric published.

  • SafetyCensus() now calls gsm.core::RunWorkflow(), which gsm.core soft-deprecated in 1.3.0 in favour of workr::RunWorkflow(). The call works and the deprecation warns once per session; taking a dependency on workr is an ecosystem-wide move rather than one this release should make on its own, and it is named here rather than left to surface as a surprise.

  • yaml moved from Suggests to Imports. The function reads the metric definitions and the report's settings from the installed workflow files at run time, which is what stops the labels, the sections and the days-per-year division from being written down twice. yaml is already a hard dependency of gsm.core, so nothing new is installed.

FDA ST&F phase 0

Phase 0 of the FDA Standard Safety Tables and Figures work (obot.roadmap#9): the guide's reference criteria arrive as package data, so every static figure that follows, and every interactive twin that wants to agree with it, reads the FDA's thresholds from one place instead of retyping them.

  • FDA_AbnormalityLevels and FDA_ExtremeValues — Appendix Tables 56 to 60 of the FDA ST&F Integrated Guide v2.0 as tested package data. The level 1, 2 and 3 abnormality criteria for chemistry and hematology (46 rows) and the extreme values suggestive of laboratory or recording error for chemistry, hematology and vital signs (40 parameters, each in US-conventional and SI units). Every row carries the guide table, section and printed page it came from and a note wherever the transcription needed a reading; the abnormality-level rows also carry each criterion as printed beside the parsed number. Spot values are asserted against the PDF page by page in the suite. Nothing in R could supply these thresholds before; now data(FDA_AbnormalityLevels) does. (#77, #83, hub obot.roadmap#9)

  • design/fda-adam-alignment.md — the ADaM alignment the design left open, settled. For each of ADSL, ADAE, ADLB and ADVS the note lists the columns the 22 figures and the phase 0 derivations need, marks each as found in the vendored example data, present in a gsm.mapping Mapped_* domain, derivable, or missing, and records a decision for every gap: which columns to vendor from pharmaverseadam (they join on the same CDISC pilot subjects), which to derive once in a shared helper, and which figures are out of scope on the demo data. It ends with the column contract the phase 1 engines code against. 51 columns, none unmarked, nothing blocked. (#80, #85, hub obot.roadmap#9)

  • Derive_ULNMultiple(), Derive_AbnormalityLevel() and Derive_ExtremeValueFlag() — the guide's first normative rules, applied once in R. Each takes long-format results in the shape of ExampleData("adbds") and returns the same frame with its derived columns added, never an aggregate: the result as a multiple of its own upper limit of normal; the level 1, 2 or 3 abnormality grade from Tables 56 and 57 with the direction and the criterion that fired; and the flag the guide's extreme-value exclusion rule reads from Tables 58 to 60. The grading and the flag honour the data's unit column: an absolute threshold is compared only in its own unit system, and a result in a unit the guide does not print is left NA and named in a message rather than misgraded. Column names are arguments with the adbds names as defaults; the criteria table is an argument too, so an established grading system can stand in for the FDA's. A cross-check asserts that the ULN multiples reproduce the peaks Input_HysLaw() computes for the same participants. (#78, #86, hub obot.roadmap#9)

  • requirements/fda-stf.md — the FDA ST&F requirement matrix. One keyed row for each of the guide's 22 figures (FDA-FIG-001 to FDA-FIG-022) and one for each cross-cutting rule the phase 0 derivations and the later static engines implement (FDA-RULE-001 to FDA-RULE-016), in the safety.viz matrix shape, so a static rendering in this package and its interactive twin in safety.viz cite one requirement ID and their evidence meets on the same row. Every row names the guide version and section, its chart engine, its ADaM domains and its safety.viz twin; requirements/README.md says how rows are keyed and how a test cites one, and a test holds the file to that shape. (#79, #84, hub obot.roadmap#9)
